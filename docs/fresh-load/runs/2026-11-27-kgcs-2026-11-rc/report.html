Findings

What surfaced by looking closely

F1
the released code reproduces the 2026-11-01 build.
Between 803dc01 and 9723057 no file under etl/ or validation/ changed; what changed is the entry points (moved to scripts/) and the downloader. Equal to the reference run: the 25 label counts, the 22 relationship types its summary recorded, the 48 values of stats.json, the counters of the 16 ETL steps, the 11 loader warnings, and the 13 sourceSnapshots of BuildMetadata (read on both databases). The only differences are pipelineCommit, buildTimestamp and the absence of the "uncommitted changes" warning: the tree was clean.
F2
load time: 69.5 min against 109.3, with two things changed at once.
The server ran with 8 GiB of heap and 12 GiB of page cache instead of the stock 1 GiB / 512 MiB, and the five other databases of the instance were stopped. On 2026-11-01 the MATCHES_PLATFORM rate started at about 0.5 min per file and doubled from about file 13 of 74; here it stayed at about 0.47 min per file to the end. That is what a store outgrowing a 512 MiB page cache looks like, but the two changes were not separated, so the cause is narrowed, not proven. This is the follow-up of F6 of the 2026-11-01 run. docs/fresh-load.md step 2 now states the memory settings.
F3
the load is serial and bounded by one server thread.
Sampled over about 10 s during MATCHES_PLATFORM: the Neo4j process used about 0.8 core and the Python client about 0.3, on a machine that was 95 % idle. Raising the process priority and closing other programs during the step changed nothing measurable (0.46 to 0.47 min per file before and after). The node phases of the cpe step were 16 to 29 % slower than on 2026-11-01; not explained.
F4
the entry points work from scripts/ and the downloader reports all 13 sources.
scripts/run_all_etl.py and the validation scripts ran with the repository's own interpreter from the repository root. scripts/download.py wrote only under its --output-dir. Its log disagrees with its own summary in three texts (Validation: 12/12 standards, CPE: 19 files, CAR: 125 files against 13, 18 and 122 in the per-source table): wording, not results.
F5
cwe_consequence_vocabulary FAIL, 3 violations, unchanged.
The same three values as F3 of the 2026-11-01 run (DoS: Prevent Access twice, Undefined Behavior once). The fix belongs to the spec vocabulary.
F6
the server version was never read from the server before.
The 2026-11-01 summary says 2026.07.x, taken from the instance's label; the server reported 2026.09.0 on 2026-11-27. Whether it was upgraded in between is not known. The procedure now asks for CALL dbms.components() in the evidence.
